# 时间敏感逻辑的测试必须用相对 now 的动态时间戳

**结论速览**：测试夹具里所有时间戳一律 `(Utc::now() ± Duration)` 动态生成、排序断言的各行用不同时间戳；禁止写死未来的"固定日期"。
适用条件：任何依赖"相对当前时刻"判定（过期/宽限/倒计时/排序）的逻辑测试。

## ✅ 固定过期时间戳与重复时间戳两次打假测试（2026-10-08）

- **为何值得记**：两次测试失败同根因——一次把"未来某天"写死成测试夹具（随真实日期推进变成过去值）、一次两行用同一时间戳让倒序断言依赖不稳定排序；不修数据修实现的话会引入真 bug。
- **最终方案**：
```rust
// 夹具时间一律相对真实 now 动态生成（如"1 小时后的重置时间"）
let resets = (Utc::now() + chrono::Duration::hours(1)).to_rfc3339();
// 排序断言的相邻行必须用不同时间戳
let ts2 = (Utc::now() + chrono::Duration::seconds(1)).to_rfc3339();
```
- **为什么这样做**：本项目的 H5 漂移检测判据是"`now > resets_at + 10min 宽限`"——夹具里写死 `"2026-10-01T07:00:00Z"` 这类字符串，测试运行的真实日期一旦越过它，快照就莫名变成 Degraded，且报错信息完全看不出与时间戳有关；倒序 `sort_by` 对相等键是稳定排序，断言"第一行是新行"在数据顺序变化时会翻转。
- **适用条件**：Rust chrono / 任意语言的相对时间判定逻辑；特别是"用真实 `Utc::now()` 而非注入时钟"的测试风格（注入时钟则不受此限，但本项目未注入）。
- **验证证据**：两次 RED→GREEN 均当场完成——poller 测试改动态 resets 后 `统计失败不降级balance成功状态` 通过；store 测试改 `ts2` 后 `requests_24h入库往返与日志携带` 通过，全套 `cargo test` 42 项绿。
- **交叉验证**：单 agent 单次跑通；两次失败-修复均在同一会话内由真实测试输出确认，无书面审查轨迹。
- **关键步骤**：审查夹具里每个硬编码时间字符串，逐个换成 `now ± Duration`；审查排序断言输入行的时间戳互异。
- **易错点**：最容易再错的是"顺手"在夹具里贴一个看起来很未来的固定日期（半年后看必炸）；以及给多行写同一个 `ts` 变量再断言顺序。
